# OrangeHRM Employee Lifecycle - UI + API Automation

Automated end-to-end test of the **Employee Lifecycle Management** scenario against the
[OrangeHRM demo site](https://opensource-demo.orangehrmlive.com/), built with
**Python + Playwright + pytest**, following the **Page Object Model (POM)**.

The single test scenario:

1. **Login** with valid credentials and verify the dashboard loads.
2. **Add a new employee** (PIM > Add Employee) using data-driven input from
   `data/employee_data.json`, including a profile picture upload.
3. **Edit the employee** - search by Employee ID, update Job Title and
   Employment Status on the Job tab.
4. **Validate via the OrangeHRM API** - the employee and job-detail changes
   are cross-checked directly against OrangeHRM's own internal REST API
   (`/api/v2/pim/employees`), reusing the authenticated browser session.
5. **Delete the employee** from the UI, and confirm the deletion both in the
   UI (search returns no results) and via the API (the employee is no longer
   returned).
6. **Logout**, and confirm the session was invalidated (a protected page
   redirects back to the login screen).

## Framework structure

```
Orange-automation/
├── config/
│   └── config.py              # Base URL, credentials, timeouts
├── data/
│   ├── employee_data.json     # Data-driven employee fixture
│   └── profile_picture.png    # Sample photo uploaded during Add Employee
├── pages/                     # Page Object Model
│   ├── base_page.py           # Shared waits/toast helper + global nav (PIM, Logout)
│   ├── login_page.py
│   ├── dashboard_page.py
│   ├── add_employee_page.py
│   ├── employee_list_page.py
│   ├── employee_profile_page.py
│   └── job_details_page.py
├── api/
│   └── employee_api_client.py # Thin client over OrangeHRM's internal REST API
├── tests/
│   └── test_employee_lifecycle.py   # The end-to-end scenario
├── conftest.py                 # pytest fixtures: employee_data, video recording
├── pytest.ini                  # pytest + reporting configuration
├── requirements.txt
├── reports/
│   └── report.html             # HTML test report (generated by pytest-html)
└── videos/
    └── employee_lifecycle_test_run.webm  # Recorded video of a full test run
```

**Design notes**

- Every page object returns the *next* page object from its action methods
  (e.g. `login_page.login(...)` returns a `DashboardPage`), so tests read as
  a linear, chainable workflow instead of juggling raw locators.
- Global, always-present navigation (the left **PIM** menu link and the
  top-right **Logout** menu) lives on `BasePage` and is inherited by every
  page object, rather than being duplicated per page.
- The internal API client reuses `page.request`, which shares cookies with
  the already-authenticated browser context - the same login session drives
  both the UI actions and the API assertions, so there is no separate
  auth/token handling to maintain.
- The Employee ID used in each run is generated at test time
  (`<prefix from JSON><timestamp>`) because the target site is a shared
  public demo instance; a hardcoded ID would eventually collide with data
  created by another user or a previous run.

## Prerequisites

- Python 3.10+
- Internet access to `opensource-demo.orangehrmlive.com`

## Setup instructions

```bash
# 1. From the project root, create and activate a virtual environment
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Download the Playwright browser binaries (one-time)
playwright install chromium
# If this is a fresh Linux machine and you have sudo access, you can instead run:
# playwright install --with-deps chromium
```

## How to run the tests

```bash
source .venv/bin/activate
pytest
```

This will, by default (configured in `pytest.ini` / `conftest.py`):

- Run `tests/test_employee_lifecycle.py` in headless Chromium.
- Record a video of the run to `videos/` (native Playwright video capture).
- Generate a self-contained HTML report at `reports/report.html`.

Useful variations:

```bash
# Run headed, so you can watch the browser live
pytest --headed

# Run in a different browser
pytest --browser firefox

# Slow the run down for easier viewing
pytest --headed --slowmo 500

# Verbose output with live log lines for each step
pytest -v
```

After the run, open the HTML report in a browser:

```bash
# e.g.
xdg-open reports/report.html   # Linux
open reports/report.html       # macOS
```

The video for the corresponding run is saved under `videos/` as a `.webm`
file (one file per test session).

## Test data

`data/employee_data.json` holds the data-driven inputs for the new employee:

```json
{
  "firstName": "Jordan",
  "lastName": "Blake",
  "employeeIdPrefix": "QA",
  "profilePicture": "data/profile_picture.png",
  "updatedJobTitle": "QA Engineer",
  "updatedEmploymentStatus": "Full-Time Permanent"
}
```

The `employee_data` fixture in `conftest.py` loads this file and appends a
unique timestamp suffix to `employeeIdPrefix` for every test run.
